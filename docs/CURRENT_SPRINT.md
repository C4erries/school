### 📋 Детальное Микро-ТЗ спринта 2.1.3

#### Задача 1: Дефолтный прайс репетитора
- **Проблема**: Каждый раз при создании нового ученика репетитор вынужден вручную вводить ставки (например, 1500, 1000, 700). Нет возможности один раз сохранить свои стандартные расценки.
- **Что делаем**:
  - В таблицу `users` добавляются поля `default_rate_individual NUMERIC(10,2) DEFAULT 1500`, `default_rate_pair NUMERIC(10,2) DEFAULT 1000`, `default_rate_group NUMERIC(10,2) DEFAULT 700`.
  - Эндпоинты: `GET /api/v1/users/me/rates` и `PUT /api/v1/users/me/rates` (или поля в `UserResponse` и `PATCH /users/me`).
  - В шапке CRM добавляется кнопка «Базовый прайс» с иконкой `Settings` / `Coins`.
  - При создании нового ученика поля ставок предзаполняются сохраненными дефолтными значениями.

#### Задача 2: Продвинутый реестр и архивация учеников
- **Проблема**: При росте базы учеников до 15–30 человек карточки занимают огромный экран; нельзя быстро найти ученика по телефону, отфильтровать должников или скрыть выпускников.
- **Что делаем**:
  - В таблице `clients` добавляется поле `is_archived BOOLEAN NOT NULL DEFAULT FALSE`.
  - Поиск в реальном времени по имени и номеру телефона (фильтрация на клиенте с дебаунсом или query-параметром).
  - Табы-фильтры статуса: «Активные» (по умолчанию), «В архиве», «Все».
  - Фильтр по балансу: «Все», «С абонементом (> 0 ч)», «Нулевой (0 ч)», «Должники (< 0 ч)».
  - Фильтр по партнерским тегам (выпадающий список или бейджи тегов).
  - В карточке ученика: действие «В архив» (скрывает ученика из активного расписания, сохраняя всю историю) и «Восстановить из архива».

#### Задача 3: Ручная корректировка баланса абонементов с аудитом
- **Проблема**: Иногда репетитор проводит компенсационный урок, отменяет ошибочное списание или дарит часы. Сейчас изменить баланс можно только фиктивной покупкой абонемента.
- **Что делаем**:
  - Создается таблица `client_balance_adjustments`: `id`, `client_id`, `teacher_id`, `format`, `delta_hours`, `reason`, `created_at`.
  - API: `POST /api/v1/clients/{id}/adjust-balance` (принимает `format`, `delta_hours` (дробное, м.б. положительным или отрицательным), `reason`).
  - На карточке ученика рядом с «Пополнить абонемент» добавляется действие «Скорректировать баланс».
  - Модалка `AdjustBalanceModal` запрашивает: формат (`individual`, `pair`, `group`), изменение часов (например, `+1.5` или `-1.0`), обязательный комментарий/причину (например, «Компенсация за технический сбой»).

#### Задача 4: Client-Side Caching (CSC) через Valkey
- **Проблема**: При частых переходах по расписанию и CRM повторяются одинаковые запросы за кабинетами (`/classrooms`), тегами (`/tags`) и профилем преподавателя.
- **Что делаем**:
  - На бэкенде подключается `client.DoCache(...)` из пакета `github.com/valkey-io/valkey-go`.
  - Кэшируются ответы справочников с TTL (например, 10–30 минут).
  - Инвалидация: при создании/удалении кабинетов или тегов кэш сбрасывается по протоколу RESP3 / явным удалением ключей.

#### Задача 5: Декомпозиция `TeacherSchedulePage.tsx` (1443 строк)
- **Проблема**: Файл на 1443 строки перегружен, в нем смешана логика позиционирования нахлёстов, три режима отображения (Day/Week/List) и две большие модалки. AI-агентам сложно и дорого вносить точечные изменения.
- **Что делаем**:
  - Создаем директорию `frontend/src/features/schedule/`:
    - `components/ScheduleWeekView.tsx` (сетка недели на 7 колонок).
    - `components/ScheduleDayView.tsx` (сетка дня).
    - `components/ScheduleListView.tsx` (список уроков).
    - `components/CreateLessonModal.tsx` (модалка создания).
    - `components/EditLessonModal.tsx` (модалка редактирования).
    - `hooks/useSchedulePositioning.ts` (хук и хелперы каскадных нахлёстов).
  - Сам файл `TeacherSchedulePage.tsx` сокращается до чистого контейнера (~150-200 строк), управляющего общим стейтом.

#### Задача 6: Декомпозиция `TeacherClientsPage.tsx` (945 строк)
