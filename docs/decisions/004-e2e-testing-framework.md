# ADR-004: E2E и интеграционное тестирование API на Python + pytest в Docker

## Статус
Принято (Accepted)

## Контекст
В проекте реализована Фаза 0 (инфраструктура, Nginx, Healthchecks, Go skeleton, React shell) и Фаза 1 (Аутентификация, JWT, Valkey сессии, PostgreSQL репозитории, ролевая модель, UI экраны).
Для обеспечения качества и надежности всей системы требуется слой интеграционного сквозного (End-to-End, E2E) тестирования:
- Существующие Go unit-тесты (`make test`) работают быстро, но изолированно и на моках.
- Необходим инструмент для автоматической black-box проверки реального стека (HTTP API через Nginx, PostgreSQL, Valkey) по бизнес-сценариям.
- Система тестов должна запускаться легко одной командой (`make test-e2e`), изолированно от хост-системы разработчика (без конфликтов версий библиотек и интерпретатора) и масштабироваться по мере появления новых фаз проекта.

## Решение
1. **Стек E2E тестирования**:
   - Язык: **Python 3.12**
   - Тестовый фреймворк: **`pytest`**
   - HTTP клиент: **`httpx`** (современный быстрый HTTP-клиент с поддержкой connection pooling и удобным синтаксисом)
   - Генерация синтетических данных: **`faker`**

2. **Изоляция и запуск в Docker**:
   - В `docker-compose.yml` регистрируется сервис `test-runner` с профилем `profiles: ["test"]` (не запускается в обычном `docker compose up`, запускается по требованию).
   - Монтирование volume `./tests:/app` позволяет редактировать и добавлять новые тесты без пересборки Docker-образа.
   - Запуск осуществляется через команду `make test-e2e` (`docker compose run --rm test-runner pytest -v`).
   - Тесты обращаются к системе внутри общей docker-сети через Nginx (`http://nginx:80`), полностью эмулируя поведение внешнего браузерного клиента.

3. **Организация структуры тестов**:
   - Директория `tests/` располагается в корне проекта отдельно от бэкенда и фронтенда.
   - Тесты группируются по фазам: `tests/api/phase1_auth/`, `tests/api/phase2_schedule/` и т.д.
   - Каждая последующая фаза сохраняет предыдущие тесты, формируя регрессионный сьют.

## Последствия
### Положительные:
- **Zero-setup**: разработчику не нужно настраивать виртуальные окружения Python на машине, достаточно Docker.
- **Высокая скорость и читаемость**: сценарии на Python и `pytest` пишутся в разы компактнее, чем на Go.
- **Black-box верификация**: проверяется реальная работа Nginx + Go + PostgreSQL + Valkey.
- **Готовность к CI/CD**: та же команда `make test-e2e` может исполняться в GitHub Actions.

### Отрицательные / Компромиссы:
- Дополнительный Docker-образ (~70 МБ).
- Типы и схемы запросов валидируются по факту выполнения HTTP-запросов, а не на этапе статической компиляции.
