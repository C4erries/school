# ADR 005: Переход на "Tutor Assistant" MVP (Отделение Client от User)

## Контекст и Проблема
Изначально архитектура предполагала, что платформа "Школа" строится на обязательной регистрации всех участников (учителей, учеников, администраторов). Сущность ученика была тесно связана с таблицей `users` (роль `student`). 
Однако в реальности репетитору на старте нужен **инструмент для себя (single-player режим)**, а не сложная платформа, где полезность зависит от того, зарегистрируется ли ученик.
Пользователь инициировал пивот: продукт должен стать SaaS-решением (помощником) для репетитора. 

**Новые требования (MVP v1 & v1.5):**
1. Ученик — это "слепая" сущность, создаваемая и управляемая самим репетитором.
2. Репетитор сам формирует свое расписание.
3. Финансовый учет: учет абонементов (пакетов занятий/часов), расчет потенциальной максимальной выручки (по расписанию) и расчет реального заработка с учетом "Тегов" учеников (например, процент комиссии школе).
4. Обязательный экспорт данных для бэкапа.

## Решение
Мы меняем архитектуру в части работы с расписанием и пользователями:

1. **Разделение User и Client:**
   - Таблица `users` используется только для реальных пользователей системы (сейчас это репетиторы/владельцы школ).
   - Создается новая таблица `clients` (или `tutor_clients`), которая содержит "глухие" профили учеников (имя, телефон, баланс/абонементы). Эта таблица привязана к `users` (кто создал клиента).
   
2. **Абонементы и Финансы:**
   - В `clients` или отдельной таблице `client_subscriptions` мы храним абонементы учеников (оплаченные часы/занятия).
   - При завершении урока баланс абонемента списывается.
   - Дашборд считает **Две метрики**:
     - *Gross Potential Revenue* (Максимально возможная выручка по текущему расписанию).
     - *Net Tutor Income* (Реальный заработок репетитора с учетом тегов/комиссий школы за этот месяц).

3. **Связка сущностей (Подготовка к MVP v3 - Школа):**
   - У `clients` будет nullable поле `user_id`. Когда мы перейдем к MVP v3 (Полноценная Школа) и дадим ученикам возможность регистрироваться, мы просто слинкуем их реальный `user_id` с их карточкой `client`.

## Последствия (Consequences)
- **Плюсы**: Резкое снижение порога входа для продукта. Репетитор может начать пользоваться платформой в первый же день. Упрощение логики флоу (не нужно подтверждение уроков от учеников).
- **Минусы**: Временно мы выбрасываем код подтверждения уроков со стороны `student` (Фаза 2), который был написан ранее, так как `student` больше не логинится в систему в MVP v1.
- **Миграции**: Потребуется написать SQL миграции для создания `clients`, `client_subscriptions` и изменения таблицы `lessons` (теперь lesson привязан к `client_id`, а не к `student_id` из `users`).
