# ADR 010: Стандарт вызова, изоляции контекста и онбординга субагентов

## Статус
Принято (Accepted)

## Контекст и Проблема
1. **Изоляция контекста субагентов**:
   При вызове субагента через инструмент `invoke_subagent`, субагент стартует в отдельном изолированном контексте выполнения диалога. Он не «помнит» предыдущие реплики пользователя и обсуждения из главного чата.
2. **Риск потери проектных соглашений**:
   Если при определении субагента (`define_subagent`) или при постановке задачи (`invoke_subagent`) явно не обязать его ознакомиться с правилами проекта (`AGENTS.md`, `docs/CONVENTIONS.md`, дизайн-система `docs/DESIGN_SYSTEM.md`), возникает риск регрессий:
   - Фронтенд-агент может использовать непрозрачные серые фоны (`bg-slate-50`) вместо Apple Liquid Glass;
   - Бэкенд-агент может нарушить структуру DDD-слоев или забыть обновить OpenAPI контракт;
   - QA-агент может написать тесты без очистки или нарушить RBAC-проверки.
3. **Необходимость единого регламента**:
   Требуется строгий, воспроизводимый регламент того, как ведущий агент (Tech Lead / Orchestrator) формулирует системные промпты, ставит задачи и контролирует результаты субагентов.

## Решение

### 1. Правило «Шага 0» (Step 0 Onboarding Rule)
Каждый субагент в своем базовом `system_prompt` и в стартовом сообщении задачи ОБЯЗАН содержать инструкцию:
> **Шаг 0**: Перед началом любых действий прочитай `AGENTS.md`, `docs/PROJECT_CONTEXT.md` и профильный раздел `docs/CONVENTIONS.md`. Это закон проекта.

### 2. Стандартизированные архетипы субагентов
В проекте фиксируются 3 ключевых типа разработчиков с преднастроенными системными промптами:
1. **`backend_developer`**:
   - Специализация: Go 1.24, PostgreSQL, OpenAPI-first (`api.yaml` -> `make oapi`), DDD архитектура (`domain/`, `application/`, `infrastructure/`).
   - Обязательный DoD: запуск `make test` (100% pass), отсутствие гонок (`-race`), строгая обработка ошибок с `fmt.Errorf("%w")`.
2. **`frontend_developer`**:
   - Специализация: React 18, TypeScript, Tailwind CSS, Vite, Lucide-react.
   - Обязательный DoD: стиль Apple Liquid Glass (`GlassCard`, `GlassModal`, `backdrop-blur-md`), модульные компоненты < 300 строк, `npm run lint && npm run build` (0 ошибок).
3. **`qa_engineer`**:
   - Специализация: Python 3.12, `pytest`, `httpx`, Docker.
   - Обязательный DoD: изолированные E2E сценарии в `tests/api/`, проверка RBAC и разделения арендаторов, успешный прогон `docker compose run --rm test-runner pytest -v`.

### 3. Структура промпта при вызове (`Prompt Contract`)
Каждое задание для субагента должно строиться по строгому 5-блочному шаблону:
1. **Контекст задачи**: ссылка на пункт в `docs/CURRENT_SPRINT.md` и ключевые ADR.
2. **Входные контракты**: ссылки на спецификацию API (`api.yaml`), миграции или типы.
3. **Четкий скоуп работ**: пошаговый список создаваемых/изменяемых файлов.
4. **Ограничения (Constraints)**: запреты (не менять стек, не трогать чужие файлы, соблюдать Liquid Glass).
5. **Критерий приемки (Verification)**: команды верификации, которые агент обязан выполнить перед завершением (`make test`, `npm run lint`, `make test-e2e`).

### 4. Режим параллельной работы (Concurrency Protocol)
- Бэкенд и фронтенд могут разрабатываться параллельно **только после** явной фиксации OpenAPI спецификации в `backend/api/openapi/api.yaml`.
- Интеграционная приемка осуществляется QA-агентом после завершения обеих сторон.

## Последствия
- Субагенты гарантированно знают архитектурный контекст и дизайн-систему с первой секунды.
- Исключаются случайные регрессии UI (появление непрозрачных элементов) и поломки тестов.
- Процесс делегирования задач становится детерминированным и прозрачным для пользователя.
