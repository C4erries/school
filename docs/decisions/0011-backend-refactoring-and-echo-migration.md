# ADR 011: Архитектурный рефакторинг бэкенда, переход на Echo v4 и декомпозиция адаптеров

## Статус
Принято (Accepted)

## Контекст и Проблематика
1. **Перегрузка плоских пакетов адаптеров**:
   В процессе активного развития Фазы 2 каталоги:
   - `backend/internal/infrastructure/api/adapters/httpserver`
   - `backend/internal/infrastructure/api/adapters/postgres`
   разрослись до 15+ файлов каждый. Все хэндлеры и репозитории находились в едином плоском пространстве имен, что затрудняло навигацию, усложняло поддержку и повышало риск циклических зависимостей.
2. **Ограничения стандартного `net/http` ServeMux**:
   Стандартный мультиплексор требует ручной обвязки контекстов, извлечения параметров путей, ручной обработки CORS и громоздкой цепочки middleware.
   Переход на современный и легковесный фреймворк **Echo v4** обеспечивает:
   - Идиоматичную работу с `echo.Context` (удобный биндинг, JSON-ответы, статус-коды);
   - Родную поддержку генератора `oapi-codegen` с флагом `echo` (генерация готового интерфейса `ServerInterface` для Echo);
   - Мощные и производительные встроенные middleware (CORS, Recover, Logger, JWT Auth).
3. **Монолитные файлы с большим количеством строк**:
   Аналогично проблеме монолитности фронтенда, решенной в [ADR-008](0008-frontend-decomposition-and-valkey-csc.md), отдельные файлы на бэкенде начали приближаться к крупным размерам. Требуется установить четкий стандарт: не более 300–400 строк на один файл кода (за исключением автогенерируемых `*.gen.go`).
4. **Тайминг рефакторинга**:
   Рефакторинг критически важно провести **до начала Фазы 2.3 (Регулярные занятия / Recurring Lessons)**, чтобы сложная логика серий уроков и исключений RFC 5545 RRULE реализовывалась уже на чистом, модульном фундаменте Echo.

## Решение

### 1. Выделение Спринта 2.2.4 (Технический долг)
Перед стартом Фазы 2.3 проводится выделенный инженерный спринт 2.2.4 по очистке и рефакторингу бэкенда.

### 2. Миграция на веб-фреймворк Echo v4
- В `go.mod` добавляется зависимость `github.com/labstack/echo/v4`.
- Конфигурация генератора `oapi-codegen` переключается на генерацию роутов и интерфейса для Echo (`echo-server`).
- Замена HTTP сервера в `cmd/api/main.go` и `server.go` на экземпляр `*echo.Echo`.
- Все HTTP-хэндлеры переводятся на сигнатуру Echo: `func(c echo.Context) error`.

### 3. Декомпозиция адаптеров по предметным доменам
Вместо монолитных плоских папок структура адаптеров делится на изолированные предметные пакеты:
```
backend/internal/infrastructure/api/adapters/
├── http/
│   ├── auth/          # хэндлеры авторизации и профиля
│   ├── crm/           # хэндлеры клиентов и абонементов
│   ├── schedule/      # хэндлеры уроков и кабинетов
│   ├── finance/       # хэндлеры платежей и выплат
│   ├── analytics/     # хэндлеры KPI, динамики и прогнозов
│   └── dashboard/     # хэндлеры командного центра
└── postgres/
    ├── auth/          # репозитории users, tokens
    ├── crm/           # репозитории clients, subscriptions
    ├── schedule/      # репозитории lessons, classrooms
    └── finance/       # репозитории payments, partner_payouts
```

### 4. Стандарт размера файлов
- Для всех рукописных файлов бэкенда вводится жесткое ограничение: **не более 300–400 строк кода**.
- При превышении объема файл декомпозируется по обязанностям (выделение хелперов, SQL-билдеров, валидаторов, мапперов).
- Правило не распространяется только на автогенерируемый файл `api.gen.go`.

## Последствия
- Высокая скорость разработки и чистота кода перед сложной Фазой 2.3.
- Значительное сокращение бойлерплейта в хэндлерах благодаря Echo v4.
- 100% совместимость со всеми существующими 56 E2E автотестами (контракт OpenAPI остается неизменным).
