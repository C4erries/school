# Руководство по оркестрации субагентов (Subagents Guide)

> Этот документ регламентирует правила вызова, передачи контекста и координации субагентов в проекте «School» в соответствии с **[ADR-010](decisions/0010-subagent-orchestration-and-prompting.md)**.

---

## 🎯 Зачем нужен этот регламент?

Субагенты запускаются в **изолированном контексте** (`conversation context`).
Они **НЕ знают** историю предыдущих обсуждений в чате и **НЕ читают** файлы проекта автоматически, если им явно не указать на это.

Без четкого протокола передачи контекста субагент может:
* Использовать обычные белые фоны (`bg-white`), сломав Apple Liquid Glass;
* Нарушить слои DDD в Go или добавить сторонние библиотеки без согласования;
* Забыть обновить OpenAPI схему или сгенерировать код;
* Не запустить линтеры и автотесты.

---

## 🧭 Золотое правило «Шага 0» (Step 0 Onboarding)

Каждый субагент в первом же действии обязан прочитать корневые правила проекта:
1. `AGENTS.md` — главные правила проекта и запреты.
2. `docs/PROJECT_CONTEXT.md` — архитектура single-player Tutor Assistant, стек и текущее состояние.
3. `docs/CONVENTIONS.md` — соглашения по написанию Go/React кода и стиль Liquid Glass.
4. `docs/CURRENT_SPRINT.md` — микро-ТЗ текущей задачи и DoD.

## 👥 Стандартные роли (Архетипы субагентов)

### 1. `backend_developer`
* **Назначение**: Реализация серверной логики на Go, миграций PostgreSQL, спецификаций OpenAPI и юнит-тестов.
* **Системный промпт (`system_prompt`)**:
  ```text
  Ты ведущий Go-разработчик проекта School (Tutor Assistant SaaS).
  Твой закон — AGENTS.md, docs/PROJECT_CONTEXT.md и docs/CONVENTIONS.md.
  Архитектура: DDD (internal/domain, internal/application, internal/infrastructure).
  Контракты: OpenAPI-first в backend/api/openapi/api.yaml с генерацией через `make oapi`.
  База данных: PostgreSQL миграции (golang-migrate).
  Тестирование: Обязательный прогон `make test` (100% зеленые юнит-тесты без data races).
  Никаких решений по изменению стека или библиотек без согласования.
  ```

### 2. `frontend_developer`
* **Назначение**: Разработка пользовательского интерфейса на React, TypeScript, Tailwind CSS и Vite.
* **Системный промпт (`system_prompt`)**:
  ```text
  Ты ведущий React/TypeScript фронтенд-разработчик проекта School (Tutor Assistant SaaS).
  Твой закон — AGENTS.md, docs/PROJECT_CONTEXT.md, docs/CONVENTIONS.md и ADR-006 (Apple Liquid Glass).
  Дизайн-система: Apple Liquid Glass (GlassCard, GlassModal, GlassButton, полупрозрачные фоны white/20-white/40 с backdrop-blur-md).
  СТРОГО ЗАПРЕЩЕНО: Непрозрачные белые/серые плашки (bg-white, bg-slate-50/100).
  Модульность: Все компоненты разбиваются по папкам features/ и должны быть строго меньше 300 строк (ADR-008).
  Проверка: Обязательный запуск `npm run lint && npm run build` (0 ошибок и предупреждений).
  ```

### 3. `qa_engineer`
* **Назначение**: Комплексное E2E тестирование в Docker, регрессионная валидация, проверка RBAC и целостности системы.
* **Системный промпт (`system_prompt`)**:
  ```text
  Ты ведущий QA Automation инженер проекта School.
  Твой закон — AGENTS.md, docs/PROJECT_CONTEXT.md и docs/CONVENTIONS.md.
  Инструменты: Python 3.12, pytest, httpx, Docker Compose.
  Зона ответственности: Написание изолированных E2E тестов в tests/api/, проверка бизнес-логики, проверка безопасности и изоляции репетиторов (RBAC/мультиарендность).
  Проверка: Обязательный прогон `make test-e2e` (или docker compose run --rm test-runner pytest -v) — 100% тестов должны быть зелеными.
  ```

## 📋 5-блочный шаблон постановки задачи субагенту

При вызове `invoke_subagent` стартовый промпт (`Prompt`) **ОБЯЗАН** содержать 5 блоков:

```text
[БЛОК 1: КОНТЕКСТ И ОНБОРДИНГ]
Привет! Твоя задача — реализовать [Название задачи] в рамках Спринта [Номер спринта].
ШАГ 0: Перед написанием кода обязательно прочитай AGENTS.md, docs/CURRENT_SPRINT.md и профильный раздел docs/CONVENTIONS.md.

[БЛОК 2: ВХОДНЫЕ КОНТРАКТЫ]
- OpenAPI контракт: backend/api/openapi/api.yaml
- Связанные ADR: docs/decisions/[номер].md
- Связанные миграции/модели: ...

[БЛОК 3: ЧЕТКИЙ СКОУП РАБОТ]
1. Создать/обновить файл A...
2. Реализовать функцию B...
3. Подключить в контейнере DI / роутах...

[БЛОК 4: ОГРАНИЧЕНИЯ И ЗАПРЕТЫ]
- Строго соблюдай архитектуру / стиль Liquid Glass.
- Не используй непрозрачные заливки / не меняй стек.
- Не трогай файлы, не относящиеся к задаче.
- ЗАПРЕЩЕНО выполнять git commit, git push, checkout и любые мутирующие команды git (разрешены только read-only: status, diff, log), если это прямо не указано в промпте.


[БЛОК 5: КРИТЕРИИ ПРИЕМКИ И ВЕРИФИКАЦИЯ]
Перед завершением обязательно выполни:
- [Для Go]: `make test`
- [Для React]: `npm run lint && npm run build`
- [Для QA]: `make test-e2e`
Убедись, что все проверки зеленые (0 ошибок). После этого пришли отчет о результатах.
```

## ⚡ Протокол параллельной разработки (Contract-First & Agent Continuity)

Когда задача требует изменений и на бэкенде, и на фронтенде, работа организуется строго по следующему 3-этапному протоколу:

### Этап 1: Фиксация OpenAPI-контракта и схемы данных (Backend Solo)
1. **Запуск бэкендера**:
   Lead-агент запускает `backend_developer` **только** с задачей подготовить фундамент контракта:
   - Создать SQL-миграцию БД (`*.up.sql` и `*.down.sql`) и доменные сущности DDD;
   - Зафиксировать схему в `backend/api/openapi/api.yaml` (DTO, пути, параметры, коды ответов);
   - Выполнить `make oapi` (генерация Echo интерфейса и типов) и создать аккуратные stub-хэндлеры для чистой компиляции (`make test`).
2. **Почему миграции обязательны на Этапе 1**:
   Схема OpenAPI и реляционная модель БД неразрывно связаны (nullable поля, форматы `DATE`/`TIMESTAMPTZ`, enum-константы, внешние ключи). Проработка миграции сразу выявляет краевые случаи схемы данных и гарантирует, что контракт API не придется переделывать посреди разработки фронтенда.
3. **Отчет родительскому агенту**:
   После успешной проверки бэкендер отправляет отчет Lead-агенту со всеми зафиксированными схемами и эндпоинтами.

### Этап 2: Параллельная реализация (Frontend + тот же агент Backend)
1. **Переиспользование бэкенд-агента (Agent Continuity)**:
   Lead-агент **НЕ создает нового бэкендера**. Он берет существующий `conversationId` агента, зафиксировавшего контракт, и отправляет ему новую задачу на реализацию бизнес-логики (репозитории, use-cases, HTTP-хэндлеры) через `send_message`.
   * *Преимущество*: у агента уже «прогрет» контекст, загружены файлы проекта и только что созданный контракт — нет потерь на онбординг.
2. **Параллельный запуск фронтендера**:
   Одновременно Lead-агент вызывает `frontend_developer` через `invoke_subagent`, передавая зафиксированный OpenAPI-контракт.
3. **Строгая изоляция рабочей области**:
   - Бэкенд работает строго в `backend/` и `tests/`.
   - Фронтенд работает строго в `frontend/`.
   - Это на 100% исключает конфликты файлов и блокировки в Git.

### Этап 3: Финальная интеграция и приемка (QA)
После того как бэкендер и фронтендер завершили свои задачи и подтвердили прохождение локальных проверок (`make test` и `npm run lint && npm run build`), Lead-агент запускает `qa_engineer` для прогона полного сьюта сквозных E2E тестов в Docker (`make test-e2e`).
